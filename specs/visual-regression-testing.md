# Visual regression testing (Playwright screenshots)

## Problem

The suites assert DOM structure, not what the page looks like — and this
app's entire product is what the page looks like. Recent bugs that
shipped past 100% unit coverage and a green e2e suite, every one caught
by a human eyeballing the screen:

- An empty two-column layout rendered as bare dashed rectangles mid-resume
  (read as a glitch; fixed by hiding empty layouts).
- The outline pane's drop gaps stuck open after a cross-zone drag
  (`dragend` never fires on a re-parented node).
- Assorted chrome/geometry drift across the top-bar, stepper, and
  two-column work — each verified by hand-inspecting screenshots during
  review, because nothing automated would have flagged them.

A small set of screenshot assertions turns "someone happened to look"
into a CI gate: any unintended pixel drift on the core surfaces fails
the build with a visual diff attached.

## Non-goals

- **No paid diff services** (Percy/Chromatic). Playwright's built-in
  `toHaveScreenshot` diffing plus the existing HTML-report artifact is
  enough at this repo's scale.
- **No PDF pixel testing.** The preview renders in the browser's plugin
  iframe — non-deterministic chrome and timing. PDF *content* fidelity
  stays covered by the existing `%PDF-` byte checks; screenshots either
  exclude the frame or mask it.
- **No exhaustive state coverage.** A handful of stable, seeded surfaces
  — not a screenshot per test. The failure mode of screenshot testing is
  drowning review in noise; scope is deliberately narrow.
- **No jsdom/component-level image snapshots.** Real browser only; jsdom
  cannot render.

## Design

### Where it lives

One new `end-to-end/tests/visual.spec.ts`, using Playwright's
`expect(page).toHaveScreenshot()`. Baseline PNGs are committed to the
repo next to the spec (Playwright's default `*-snapshots/` directory).

### Surfaces (all from deterministic seeded state)

1. **Canvas, example resume** — the prepopulated 11-block resume a
   first-time visitor sees (the localStorage fallback the e2e fixture
   already relies on).
2. **Canvas, two-column layout** — one seeded resume with a DOUBLE
   layout: both halves filled, and a second shot with one half empty
   (guards the blank-half geometry that mirrors the PDF).
3. **Empty-state CTA** — the "Your resume is empty" card.
4. **Restructure view** — styled preview + staging outline, seeded
   resume (guards both panes of the mirror).
5. **Canvas edit panel** — a block focused, panel docked beside the
   canvas (guards the gutter geometry).
6. **PDF view shell** — the inline preview open, both preview iframes
   masked (their pixels are the browser plugin's, not ours); guards the
   view's own chrome and layout (resolved open question — included from
   day one, dropped to a follow-up only if it flunks the stability
   gate).

### Determinism rules

- `animations: 'disabled'` and `caret: 'hide'` on every assertion
  (Playwright freezes CSS animations/transitions at their end state).
- Wait for `document.fonts.ready` before shooting.
- **Mask the timing-dependent chrome**: the page-count badge (appears
  after the ~1.75s render debounce) and the transient "Saved" indicator.
  Masking beats waiting — the shot stays stable regardless of render
  timing.
- The version tag in the control bar (`v0.1.0`) changes every release
  and would invalidate every baseline; mask it too.
- Fixed viewport (the suite's existing 1280×2400), `fullPage: false` —
  the top viewport-height is where all five surfaces live.

### Baseline policy (the part that makes or breaks this)

- **Baselines are Linux-Chromium only, generated by CI — never
  locally.** macOS font rendering differs per-pixel from CI's Ubuntu;
  locally generated baselines would fail every CI run and vice versa.
- Locally the visual spec **skips by default** (`test.skip` unless
  `process.platform === 'linux'` or `RUN_VISUAL=1`), so `pnpm test:e2e`
  on a Mac stays green and flake-free. Anyone who wants to run them
  locally uses Playwright's Docker image.
- **Updating baselines on an intentional visual change**: download the
  `actual` PNGs from the failing CI run's existing `playwright-report`
  artifact and commit them as the new baselines. (A
  `workflow_dispatch` job that runs `--update-snapshots` and pushes a
  commit is the fancier alternative — deliberately deferred until the
  manual flow proves annoying.)
- `maxDiffPixelRatio` tolerance starts at `0.001` (0.1%); tightened or
  loosened once real runs show the noise floor. Anti-aliasing wiggle is
  the target, not layout drift.

### CI wiring

No new workflow: the visual spec rides the existing `e2e.yml`
(ubuntu-latest + Chromium), where the platform gate passes and the
committed baselines match. On failure the uploaded `playwright-report`
artifact already contains expected/actual/diff images.

## Acceptance criteria

- [ ] `visual.spec.ts` covers the five surfaces above from seeded state,
      with the masks and determinism rules applied.
- [ ] Linux-Chromium baselines are committed; the e2e workflow fails on
      pixel drift beyond tolerance and the report artifact shows the
      diff.
- [ ] The visual spec is skipped on non-Linux by default; the rest of
      the e2e suite is unaffected locally.
- [ ] Stability proven: the visual spec passes 3 consecutive CI runs
      with no baseline churn before this spec flips to `implemented`.
- [ ] The baseline-update procedure is documented (README section in
      `end-to-end/` or comments at the top of the spec file).

## Open questions

All resolved at review (2026-07-26):

- **PDF view shell: included as a sixth surface.** The preview iframes
  (visible + staging frames) are masked; the shot guards the view's
  chrome — sr-only heading aside, the layout and (when editing) the
  docked panel. If it flunks the 3-run stability gate, it gets dropped
  to a follow-up rather than holding the other five hostage.
- **Tolerance starts at `0.001`**, settled empirically by the stability
  gate.
- **The auto-update `workflow_dispatch` job is built now**, not
  deferred: a manually triggered workflow reruns the visual spec with
  `--update-snapshots` and pushes a baseline-refresh commit to the
  branch it was dispatched on. The manual artifact-download flow remains
  documented as the fallback (and is how the very first baselines are
  bootstrapped, since `workflow_dispatch` only works once the workflow
  file is on the default branch). To support that flow, the e2e workflow
  uploads `end-to-end/test-results/` (readable `*-actual.png` files)
  alongside the existing HTML report.
